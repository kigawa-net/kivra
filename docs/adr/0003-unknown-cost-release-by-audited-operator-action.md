# ADR 0003: 価格不明(UNKNOWN_COST)の解除は、監査つきの運用者の明示操作のみで行う

- ステータス: 採用(Accepted)
- 日付: 2026-10-15
- 関連: Issue #73(価格不明の使用が、真偽値の CostCheck で予算承認を通る問題)、#109(予算)、#71(プロバイダ別の能力表)

## 背景

価格が不明な呼び出し、使用量が不完全な呼び出し、応答を失った呼び出しは、予算上「実コストが分からない」状態になる。
`DbBudgetStore` は、`unpriced_calls > 0` のスコープへの予約を `UNKNOWN_COST` で拒否する。
一方、この状態を解除する手段はまだ決まっていなかった。また、4xx と 429 のように HTTP 応答を伴う失敗が、
課金されたかどうかを断定できるかも論点だった。

## 決定

1. 価格不明・使用量不完全・応答喪失などで `unpriced_calls > 0` となったスコープは、以後の予約を `UNKNOWN_COST` で拒否し続ける(fail-closed)。
2. 解除は自動で行わない。運用者が、根拠(照合した請求額や証跡)と承認者を記録した、監査可能な明示操作でのみ行う。
   この操作は `acknowledgeUnpriced` 相当とし、台帳に解除のイベントを追記し、実コストを確定して補正する。
3. この操作の実装は B3 以降とする。**今は未実装**。現状は解除手段が無く、拒否され続ける。これは安全側の既知の制限として扱う。
4. 4xx と 429(HTTP 応答を伴う失敗)は、課金の有無を断定できないため「送信済みの可能性あり」として扱い、同一 requestId の再試行をしない。
   課金されないと明示されたステータスだけを緩和の対象とする。その緩和は、プロバイダ別の能力表(#71)に基づいて後から行う。

## 根拠

- 課金の実態が不明なまま予約を通すと、予算の上限を超える支出が静かに発生する。fail-closed がこの問題の安全な既定値である。
- 自動解除では、障害や欠損が「価格不明が解消した」と誤認される。根拠を人が記録することで、後から照合できる。
- 4xx / 429 を「未送信」と扱うと、課金された呼び出しを二重に送ることになる。

## 結果

- 影響: 価格不明が発生したスコープは、解除の操作が実装されるまで新規の予約ができない。解除の操作が無いため、その回復手段は現状の運用には無い(B3 で実装する)。
- やらないこと: 自動解除、時間経過による解除、ステータスコードだけによる「課金されていない」という判定。

## 見直しの条件

- B3 で明示操作を実装するとき(本 ADR の決定 2 の仕様をそのまま実装する)。
- プロバイダ別の能力表(#71)で、特定のステータスが課金されないと実証されたとき(決定 4 の緩和)。

## 実装状況

- 済: `unpriced_calls > 0` のスコープを `UNKNOWN_COST` で拒否する(`DbBudgetStore`、V10)。
- 未実装: `acknowledgeUnpriced` 相当の解除操作、解除イベントの台帳への追記(B3 以降)。
- 未実装: 4xx / 429 の課金有無に基づく緩和(#71 の能力表に依存)。
- 別作業: 4xx / 429 の分類そのもの(Transient / Unknown)は #72 で確認中。本 ADR はその分類を前提に「送信済みの可能性あり」として扱う。
