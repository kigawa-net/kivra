# ADR 0003: 価格不明(UNKNOWN_COST)の解除は、監査つきの運用者の明示操作のみで行う

- ステータス: 採用(Accepted)
- 日付: 2026-10-15
- 関連: Issue #73(価格不明の使用が、真偽値の CostCheck で予算承認を通る問題)、#109(予算)、#71(プロバイダ別の能力表)

## 背景

価格が不明な呼び出し、使用量が不完全な呼び出し、応答を失った呼び出しは、予算上「実コストが分からない」状態になる。
`DbBudgetStore` は、`unpriced_calls > 0` のスコープへの予約を `UNKNOWN_COST` で拒否する。
一方、この状態を解除する手段はまだ決まっていなかった。また、4xx と 429 のように HTTP 応答を伴う失敗が、
課金されたかどうかを断定できるかも論点だった。

## 決定

1. 価格不明・使用量不完全・応答喪失などで `unpriced_calls > 0` となったスコープは、以後の予約を `UNKNOWN_COST` で拒否し続ける(fail-closed)。
2. 解除は自動で行わない。運用者が、根拠(照合した請求額や証跡)と承認者を記録した、監査可能な明示操作でのみ行う。
   この操作は `acknowledgeUnpriced` 相当とし、台帳に解除のイベントを追記し、実コストを確定して補正する。
3. この操作の実装は B3 以降とする。**今は未実装**。現状は解除手段が無く、拒否され続ける。これは安全側の既知の制限として扱う。
4. 4xx と 429(HTTP 応答を伴う失敗)は、課金の有無を断定できないため「送信済みの可能性あり」として扱い、同一 requestId の再試行をしない。
   課金されないと明示されたステータスだけを緩和の対象とする。その緩和は、プロバイダ別の能力表(#71)に基づいて後から行う。

## 根拠

- 課金の実態が不明なまま予約を通すと、予算の上限を超える支出が静かに発生する。fail-closed がこの問題の安全な既定値である。
- 自動解除では、障害や欠損が「価格不明が解消した」と誤認される。根拠を人が記録することで、後から照合できる。
- 4xx / 429 を「未送信」と扱うと、課金された呼び出しを二重に送ることになる。

## 結果

- 影響: 価格不明が発生したスコープは、解除の操作が実装されるまで新規の予約ができない。解除の操作が無いため、その回復手段は現状の運用には無い(B3 で実装する)。
- やらないこと: 自動解除、時間経過による解除、ステータスコードだけによる「課金されていない」という判定。(2026-11-15 追補で、猶予を過ぎた予約を上限額で確定する自動解除に限って変更した。末尾の追補を参照)

## 見直しの条件

- B3 で明示操作を実装するとき(本 ADR の決定 2 の仕様をそのまま実装する)。
- プロバイダ別の能力表(#71)で、特定のステータスが課金されないと実証されたとき(決定 4 の緩和)。

## 実装状況

- 済: `unpriced_calls > 0` のスコープを `UNKNOWN_COST` で拒否する(`DbBudgetStore`、V10)。
- 済: `acknowledgeUnpriced` 相当の解除操作(`BudgetPort.acknowledgeUnpriced`、`DbBudgetStore` と `BudgetController`。監査の記録は V12 の `budget_acknowledgements`、HTTP は `POST /api/admin/budget/acknowledge`)。本番への配線は未実施(⑥ の PR)。
- 未実装: 4xx / 429 の課金有無に基づく緩和(#71 の能力表に依存)。
- 別作業: 4xx / 429 の分類そのもの(Transient / Unknown)は #72 で確認中。本 ADR はその分類を前提に「送信済みの可能性あり」として扱う。

## 追補 2026-11-15: 猶予を過ぎた費用不明の予約を、上限額で自動解除する

- **ユーザーの決定(2026-11-15)**: 解放も自動で行う。dev で費用不明の予約が残り、`coding claim refused: code=UNKNOWN_COST costReason=UNPRICED_IN_SCOPE` で agent が Run を取得できなくなったため。本 ADR の決定 2(解除は自動で行わない)と「やらないこと」の「自動解除、時間経過による解除」を、次の形に限って変更する。運用者の手動解除(`POST /api/admin/budget/acknowledge`)はそのまま残す。
- **確定する額は上限額**: 自動解除は実額を「不明」とし、予約の計上額(予約額。その呼び出しの上限として見積もった額。LAPSED で後から実額が分かったものはその額)のまま確定する。0 円にはしない。支出を最大に見積もって計上するので、予算を静かに超えることは無く、fail-closed の目的(見えない支出を防ぐ)は保たれる。残枠が足りなくなっても解除は行い(計上は現実の最悪値)、以後の予約が通常の上限で拒否される。
- **計上額が 0 円の予約は自動解除しない**: 為替が使えないときの CLI の見積もりなどは 0 円で計上されていて、上限額が分からない。これを確定すると支出を隠すので、従来どおり運用者の解除を待つ。
- **猶予**: 費用不明になってから(UNPRICED は確定時刻、LAPSED は予約の期限から)`KIVRA_BUDGET_UNPRICED_AUTO_RELEASE_GRACE_SECONDS`(既定 600 秒、下限 60 秒)を過ぎたものだけ。猶予の間に実額が判明する余地と、運用者が手動で確認する余地を残す。
- **スイッチ**: `KIVRA_BUDGET_UNPRICED_AUTO_RELEASE_ENABLED`。コードの既定は false(有効化は k8s のマニフェスト)。不正値は起動失敗で、値は出さない。
- **同じ経路・監査**: 解除は `DbBudgetStore.acknowledgeUnpriced`(手動と同じ検査、同じ台帳の更新、同じ監査行)を通す。二重実装しない。監査行は、承認者が固定の主体 `system:auto-release`(実在の運用者を装わない。運用者の owner key は `system:` で始まらない)、理由が固定コード `AUTO_UPPER_BOUND`、根拠が固定コード `GRACE_ELAPSED`、`actual_known = false`。既存の列で区別できるため、マイグレーションは追加しない。ログは件数と固定コードだけ。
- **安全弁**: 60 秒ごとの 1 回で最大 50 件。複数の Pod が同時に動いても、解除はテナントのロックの中で行われ、既に解除済みの予約は `AlreadyAcknowledged` で、二重に計上しない。失敗した予約は次の回に再試行され、例外はクラス名だけを記録してワーカーは止まらない。
- **範囲**: テナント、プロジェクト(`project:<id>`)、日次(`<tenant>:daily`)、run(期間 ALL)のどのスコープの予約も同じ扱い(1 件の解除で、その予約の全スコープの未価格数が 1 減る。手動の acknowledge と同じ)。費用不明の理由(価格不明、使用量の不完全、応答の喪失、TTL 切れ)は区別しない。
- **見える化**: `GET /api/admin/budget/status` に `autoReleasedCount`(累計)と `lastAutoReleaseAt`(直近)を加えた。管理画面への表示は未実装。
